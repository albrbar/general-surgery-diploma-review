## 1. الغرض والنطاق

تنظم هذه الوثيقة العلاقة بين **مجلد Google Drive الأصلي «GS diploma»** (مصدر الحقيقة الخام) و**منطقة العمل التنفيذية GS_PLATFORM** و**مستودع GitHub** الذي تُبنى منه المنصة (React/Vite + JSON). الهدف: مسار بيانات نظيف، بلا تكرارات، بمعرفات ثابتة، جاهز للمزامنة الآلية دون أي تدخل يدوي في الأصول.

خارج نطاق هذه الوثيقة: واجهات المنصة البرمجية، وبيانات الطلبة الشخصية، وأي محتوى غير تابع للدبلومة.

## 2. مبادئ الحوكمة

1. **مبدأ الحقيقة الواحدة:** الأصل `GS diploma` هو مصدر الحقيقة الخام، ويُعامل **للقراءة فقط (Read-Only)**. لا يُعدل، ولا يُحذف، ولا يُنقل منه أي ملف أساسي.
2. **مبدأ النسخ فقط (Copy-Only):** كل إعادة تنظيم تتم في `GS_PLATFORM` المولّدة آلياً بجوار الأصل، عبر `gs_drive_governance.py` الذي لا يملك أي أمر حذف أو نقل.
3. **فصل المصدر عن التصدير:** ما يصل إلى المستودع هو مخرجات معالجة (JSON مطبّع) من `01_DATA`، وليس الملفات الخام.
4. **الأتمتة قبل اليدوي:** أي ترتيب قابل للبرمجة يجب أن يمر عبر المحرك حتى يبقى قابلاً للتكرار والتدقيق.

### مصفوفة الصلاحيات

| المنطقة | قراءة | كتابة/تصدير | من يملك القرار |
|---|---|---|---|
| `GS diploma` (الأصل) | الجميع | **ممنوعة** (Read-Only) | مالك الأصل فقط |
| `GS_PLATFORM/01_DATA` | فريق المحتوى | محرك الحوكمة فقط | مراجع الـ PR |
| `GS_PLATFORM/02_SERVICES_WORKSPACE` | فريق المحتوى | الفريق + المحرك | قائد المحتوى |
| `GS_PLATFORM/00_GOVERNANCE` | الجميع | المحرك + أمين الوثائق | مراجعة ثنائية |
| `03_REVIEW_QUEUE` | فريق المحتوى | الفريق | من يفتح الـ Issue |

### أماكن الحفظ المعتمدة (قاعدة Manus)

1. كل مخلفات التعاون — وثيقة الحالة هذه، تقارير التدقيق، نسخ المحرك، مخرجات المراحل — تُحفظ **حصراً داخل Google Drive** في مجلد التعاون المشترك:
   `MyDrive/Manus/GSDIPLOMAREVISION/` (اختصار `ROOT`؛ إن اختلف اسم مجلد Manus عندك يُضبط من سطر واحد في خلية التشغيل).
   - `ROOT/docs/` الوثيقة الحاملة للحالة وسجل الإصدارات.
   - `ROOT/PHASES/phase-01_audit/ … phase-04_sync/` مخرجات كل مرحلة وتقاريرها وسجلات تشغيلها.
   - `ROOT/engine/` النسخة المعتمدة الجارية من `gs_drive_governance.py`.
2. لا تُكتب أي ملفات في Drive خارج مجلد التعاون هذا أثناء التدقيق (المرحلة 1): محرك Dry-run يعمل على مجلد مؤقت خارج Drive ثم تُنقل التقارير إلى `ROOT/PHASES/`.
3. منطقة تصدير البيانات `GS_PLATFORM` تُبنى افتراضياً **داخل مجلد Manus** (`ROOT/GS_PLATFORM`) تطبيقاً لقاعدة الحفظ الحصري (قرار v1.1 المحدّث في M2)؛ إن رغب الفريق بوضعها بجوار الأصل يكفي تغيير سطر `WORK` في خلية M2 (خيار `--work`).
4. محادثة المنصة تُستخدم للنقل والتحليل فقط؛ **النسخة المعتمدة دائماً هي النسخة في Drive**.

## 4. نظام المعرفات الثابتة (Stable IDs)

الصيغة الرسمية: **`GS-<SUBJECT>-<NNNN>`** حيث `SUBJECT` من جدول الرموز المعتمد و`NNNN` رقم تسلسلي من 0001.

| الرمز | المادة | | الرمز | المادة |
|---|---|---|---|---|
| `ABD` | الجراحة العامة — البطن والجهاز الهضمي | | `VASC` | جراحة الأوعية الدموية |
| `BRST` | جراحة الثدي | | `THOR` | جراحة الصدر |
| `TRA` | جراحة الرضوح | | `CRIT` | العناية المركزة الجراحية |
| `ENDO` | جراحة الغدد الصمّاء | | `GEN` | عامة متعددة التخصصات |
| `PEDS` | جراحة الأطفال | | `CRST` | الجراحة الكولوركتالية |

**قواعد صارمة:**

1. المعرف **فريد وثابت مدى الحياة**: يُحفظ في `ID_REGISTRY.json` مع بصمة السؤال (SHA-1 لنص السؤال والخيارات والإجابة) فلا يتغير عند إعادة التشغيل أو إعادة الترتيب.
2. المعرف الصحيح الموجود مسبقاً يُحفظ كما هو؛ المفقود أو المخالف يُخصص آلياً بالتسلسل مع تجاوز الأرقام المحجوزة.
3. ممنوع استخدام معرفات مؤقتة (`Q1`, `tmp-12`) في أي ملف يصل إلى `01_DATA`.
4. حذف سؤال لا يعيد تدوير رقمه؛ الفجوات تُوثَّق في تقرير الفجوات (gaps) ولا تُملأ إلا بسؤال جديد بنفس المادة.
5. أي تغيير في رموز المواد يمر عبر PR يعالج `ID_REGISTRY.json` و`syllabus/subject_codes.json` معاً.

## 5. مخطط سؤال JSON المعتمد

كل سؤال بعد التطبيع يحمل الحقول التالية (تُقبل المرادفات العربية عند الإدخال وتُوَّحد آلياً):

| الحقل | النوع | الوصف | المرادفات العربية المقبولة |
|---|---|---|---|
| `id` | نص | المعرف الثابت `GS-XXX-0001` | معرف، رقم السؤال |
| `subject` | رمز | من جدول المواد العشرة | المادة، التخصص، المحور |
| `stem` | نص | نص السؤال (إلزامي) | السؤال، نص السؤال |
| `options` | مصفوفة | الخيارات (2 على الأقل، القياسي 4-5) | الخيارات، الاختيارات |
| `answer_index` | رقم | فهرس الإجابة الصحيحة 0-based | الإجابة، الجواب (نص/حرف/رقم) |
| `answer_letter` | حرف | A,B,C… مشتق آلياً | — |
| `explanation` | نص | شرح الإجابة | الشرح، التفسير |
| `difficulty` | قيمة | easy / medium / hard | الصعوبة، المستوى |
| `status` | قيمة | approved / draft | الحالة، الاعتماد |
| `high_yield` | منطقي | انتماء للبنك المكثف | هاي يلد، مكثف، هام |
| `source` | نص | المرجع التعليمي | المصدر، المرجع |
| `origin_file` | نص | مسار الملف الأصلي في Drive (مشتق آلياً) | — |

## 6. دورة الاعتماد: من مسودة إلى معتمد

الاعتماد يعتمد على حقل `status` داخل كل سؤال، مع فصل مجلدات التصدير:

| قيمة `status` (بالعربية أو الإنجليزية) | التفسير | مجلد التصدير |
|---|---|---|
| معتمد / نهائي / مقبول / approved / final / published | معتمد للنشر | `question-bank/approved/` |
| مسودة / قيد المراجعة / غير معتمد / draft / pending / review | غير معتمد | `question-bank/drafts/` |
| حقل غائب أو قيمة غير معروفة | **الافتراض الآمن: مسودة** | `question-bank/drafts/` |

**مسار الترقية:** مسودة في `drafts/` → مراجعة بشرية عبر Issue مخصص → اعتماد قائد المحتوى → تشغيل المحرك فيفرق السؤال آلياً إلى `approved/` → PR مرتبط بالـ Issue → دمج بعد مراجعة ثانية. لا يُعدَّل `status` يدوياً داخل ملفات `01_DATA`؛ يُعدَّل في المصدر ثم يُعاد التشغيل.

## 7. حوكمة التكرارات والفجوات

- **تكرار الملفات:** يُكتشف ببصمة المحتوى SHA-256، وبتشابه الاسم بعد التطبيع العربي (توحيد الألف/الهاء/الياء وإزالة التشكيل). يُسجل في `DUPLICATES.csv` مع المرجع والمكرر وتوصية الأرشفة البشرية — **لا حذف آلي إطلاقاً**.
- **اختيار المرجع:** عند تساوي المحتوى يُختار الملف الأنظف مرجعاً (الملف الذي لا يحمل علامات «نسخة/backup/copy/قديم»).
- **تكرار الأسئلة:** بصمة نصية لنص السؤال + الخيارات + الإجابة؛ المتكرر يُستبعد من التصدير ويبقى في الأصل، ويُوثَّق أولُ معرفٍ احتفظ به.
- **فجوات المعرفات:** الأرقام المستخدمة لكل مادة تُفحص دورياً؛ أي فجوة تظهر في `VALIDATION_REPORT.md` وتُقرر بشرياً (سؤال محذوف؟ ملف مفقود؟).
- **أسئلة غير صالحة:** نص فارغ، أقل من خيارين، إجابة غير قابلة للتحديد — تُدرج بالملف والموضع والسبب لتُصلح في المصدر.

## 9. خط المزامنة مع مستودع GitHub

```
GS diploma (قراءة فقط)
      │  مسح + تطبيع + معرفات + فصل اعتماد
      ▼
GS_PLATFORM/01_DATA  ←  نقطة المزامنة الوحيدة
      │  رفع إلى فرع مخصص
      ▼
فرع content/issue-<N>-<موضوع>  →  Pull Request  →  مراجعة ثانية  →  main (محمي)
```

**قواعد:**

1. لا يُرفع أي ملف من الأصل مباشرة إلى المستودع؛ الرفع من `01_DATA` فقط.
2. كل رفع يرتبط بـ Issue واحد واضح، ويُفحص آلياً: صلاحية JSON، اكتمال الحقول، تفرّد المعرفات، مطابقة الخيارات.
3. `main` محمي منطقياً: كل التغييرات عبر PR مع مراجعة عضو آخر.
4. `ID_REGISTRY.json` جزء من المستودع؛ لا يُولَّد محلياً بمعزل عن سجل المستودع.
5. عند تعارض تعديلات الملف نفسه: مراجعة بشرية قبل اختيار النسخة النهائية (قاعدة المستودع القائمة).

## 10. إجراءات تشغيل محرك الحوكمة

في نوتبوك جلسة العمل الهندسية (بعد تركيب Drive):

```bash
# 1) مسح تدقيقي دون أي كتابة في الهيكل (التقارير في _AUDIT_<توقيت>)
python3 gs_drive_governance.py \
  --source "/content/drive/MyDrive/GS diploma" \
  --work   "/content/drive/MyDrive/GS_PLATFORM"

# 2) تنفيذ التصدير الكامل (بناء الهيكل + 01_DATA + التقارير)
python3 gs_drive_governance.py \
  --source "/content/drive/MyDrive/GS diploma" \
  --work   "/content/drive/MyDrive/GS_PLATFORM" --apply

# 3) اختياري: حزمة مضغوطة لرفعها إلى فرع الـ Issue
python3 gs_drive_governance.py --source "/content/drive/MyDrive/GS diploma" \
  --work "/content/drive/MyDrive/GS_PLATFORM" --apply --zip
```

**ضوابط التشغيل:** `--apply` يعيد استخدام سجل المعرفات السابق فلا تُخصَّص أرقام جديدة لأسئلة قديمة. الفيديوهات تُفهرس فقط؛ لنسخها فعلياً أضف `--copy-media` (بطيء على Drive). السقف الافتراضي للبصمة 150 ميغابايت وللنسخ 25 ميغابايت، ويُعدَّلان عبر `--max-hash-mb` و`--max-copy-mb`.

**الجدولة الموصى بها:** تدقيق (dry-run) قبل كل جلسة محتوى، وتصدير كامل (apply) قبل كل PR، ومراجعة `DUPLICATES.csv` و`VALIDATION_REPORT.md` في كل مرة.
